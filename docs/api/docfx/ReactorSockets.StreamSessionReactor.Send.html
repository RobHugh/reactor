Send(PeerId, ReadOnlySpan<byte>)

Frames message as a u32 big-endian length prefix followed by its bytes (ReactorSockets.Session.MessageFramingCodec, ADR 0010) and appends the framed bytes to peer's retention region. Nothing is written to the socket here, ever (write batching) — a successful append only sets this Peer's pending-write marker (ReactorSockets.StreamSessionReactor.PeerSlot.HasPendingRetentionWrite), which the next Pump()'s explicit flush step (ReactorSockets.StreamSessionReactor.FlushPendingRetentionWrites()) drains in a single write carrying everything queued, including whatever was already sitting there. A Send with no following Pump call puts nothing on the wire. Refuses once a Goodbye has passed in either direction — this end's own (ReactorSockets.StreamSessionReactor.PeerSlot.LocalGoodbyeSent) or the far end's arrived and this Peer is already PeerClosing or on its way to PeerClosed (ReactorSockets.StreamSessionReactor.PeerSlot.PendingCloseReasonAfterRetentionDrains) — since a Message queued after a Goodbye is not one the far end has any business receiving. Also refuses a Peer whose handshake has not reached ReactorSockets.StreamSessionReactor.HandshakeState.Established with NotEstablished: flushing that Message would write to a socket whose connect has not resolved, closing the Peer with TransportFailed, or send it before the far end's handshake record has been read.

public SendOutcome Send(PeerId peer, ReadOnlySpan<byte> message)

Parameters

peer PeerId

The Peer to send to. Throws if not open, matching CountersOf(PeerId).

message ReadOnlySpan<byte>

The Message payload, unframed. Throws if empty or longer than MaxMessageSize — the same bounds the receive side enforces, so this can never frame a Message the far end would reject.

Returns

SendOutcome

Remarks

ReactorSockets.StreamSessionReactor.PeerSlot.IsInterrupted is deliberately not one of the refusal conditions above (ADR 0010's backpressure rule): a Send against an Interrupted Peer is exactly as welcome as one against a live Peer, because holding retention across the interruption for a possible Resume is the entire point of not closing the Peer in the first place. The append behaves identically either way — the difference is only downstream, in ReactorSockets.StreamSessionReactor.FlushRetention(ReactorSockets.Core.SlotHandle, ReactorSockets.StreamSessionReactor.PeerSlot)'s own IsInterrupted guard, which leaves these bytes queued rather than attempting a dead socket. Once the ring genuinely has no room, ReactorSockets.Core.RetentionOutcome.Exhausted reports the same way it would for a live Peer — the ring does not know or care why nothing has drained it — so an interruption that outlasts the send rate reaches RetentionExhausted exactly like a single oversized Message or a sustained rate would, the third of the three paths ADR 0010 names to it.
