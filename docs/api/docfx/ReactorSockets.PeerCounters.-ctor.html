PeerCounters(ulong, ulong, ulong, ulong, ulong, ulong, ulong, ulong, ulong, ulong, ulong, ulong)

A point-in-time snapshot of one Peer's counters (ADR 0013): monotonic figures running from that Peer's establishment, with no reset, fetched by value and keyed by PeerId — mirrors LinkCounters's Raw-profile shape and the same "no accessor enumerates every Peer's counters in one call" rule.

public PeerCounters(ulong MessagesReceived, ulong RetentionHighWaterBytes, ulong Resumes, ulong OutOfWindowPackets, ulong DuplicatePackets, ulong UnreliableLossPackets, ulong HorizonDeferrals, ulong PacketsRetransmitted, ulong BytesSent, ulong BytesReceived, ulong SocketWrites, ulong ReadShareExhaustions)

Parameters

MessagesReceived ulong

Whole Messages handed to the frame arena for delivery — incremented at that point only, never when a Message's bytes finish arriving or while it sits buffered waiting for a read share or arena room. This is what makes a share exhaustion visible: a Frame in which bytes plainly arrived but this figure did not move is a Message still buffered, not one dropped. Not derivable: byte figures include framing and handshake bytes and say nothing of how many Messages they carried.

RetentionHighWaterBytes ulong

The most bytes this Peer's retention ring has ever held at once (written minus released) since the Peer was established — HighWaterBytes(int) read fresh at snapshot time, never pushed. Monotonic for the Peer's lifetime: draining the ring after a burst lowers what is currently retained but never lowers this figure. Not derivable: bytes sent is a running total, and how much of it was unacknowledged at once is what sizes retention.

Resumes ulong

How many times this Peer's transport has been successfully resumed after an Interruption (ADR 0013). Incremented once per PeerResumed raised for this Peer, on both the listening and dialling sides, and never on a refused resume. Earns its own member rather than being derived by the consumer counting PeerResumed Events: a Session profile drains Events into whatever cadence the consumer chooses, so counting them back out is not generally possible once drained, while this figure is a Counter — read fresh by value at any time, the same as every other figure here. Monotonic and never reset: a resume carries no counter's history away with it, so a retransmission count spanning several resumes is how a flapping path shows itself instead of being hidden by a zeroing on every reconnect. Not derivable: no other counter moves only on a Resume.

OutOfWindowPackets ulong

How many packet records this Peer's per-Space receive window has classified as out of window — a sequence number too far ahead of, or behind, that Space's receive window base to be tracked against it (ADR 0013). Recurs every Pump under sustained loss or reordering, which is exactly why it is a Counter and never a Diagnostic. Incremented by the parse loop's classification of each arriving record; a freshly connected Peer reads zero. Note that only the two reliable Spaces raise this on a far-ahead arrival: the unreliable Spaces slide their window forward instead and count the retirement as loss, so for those Spaces out-of-window means a sequence below the base alone. A ReliableOrdered record the window would admit but the Space will not hold behind a gap counts here too, because it is refused the same way and comes back by retransmission. Moves only on the datagram profile. Not derivable: bytes received counts these records together with admitted ones, and no other figure separates reordering beyond the window from repeats.

DuplicatePackets ulong

How many packet records this Peer's per-Space receive window has classified as duplicates — a sequence number already accounted for, most often a retransmission the far end sent because it never saw this end's acknowledgement rather than a protocol violation (ADR 0013). Recurs every Pump under sustained loss exactly like OutOfWindowPackets, and for the same reason is a Counter. Incremented by the parse loop's classification of each arriving record; a freshly connected Peer reads zero. The plain Unreliable Space contributes from a second place as well (ADR 0017): that Space suppresses repeats within its own bounded 64-sequence window, a protocol constant rather than the receive window, and a repeat that window catches after the receive window admitted it raises this figure. A repeat the receive window itself refused is counted there instead — most often on OutOfWindowPackets, since a repeat usually arrives below a base that has already passed it — so one record raises one figure and never both. A repeat delayed past those 64 sequences is delivered and raises neither: suppression there is bounded by design, and these figures count what was refused rather than what was repeated. Moves only on the datagram profile. Not derivable: this end's retransmissions are PacketsRetransmitted, and only this figure sees the far end's, from the receiving side.

UnreliableLossPackets ulong

How many sequences an unreliable Space's receive window has lost — retired by sliding its base forward before that sequence ever arrived (ADR 0013). A gap is provisional until the window passes it by: a sequence still inside the window may yet arrive late and be admitted without ever touching this figure, so it reflects only sequences a window has moved past, never every sequence not yet seen. This is one figure covering both unreliable Spaces — Unreliable and UnreliableSequenced — summed, exactly as OutOfWindowPackets and DuplicatePackets already cover all four Spaces summed, so per-Space loss is not separable from it. The two reliable Spaces never contribute, because their windows do not slide: retransmission is what fills their holes, and what they refuse lands on OutOfWindowPackets instead. No Diagnostic accompanies a gap in either Space; a lossy path must not fill the Sink with volume. Monotonic and never reset, exactly like OutOfWindowPackets; a freshly connected Peer reads zero. Moves only on the datagram profile. Not derivable: a sequence that never arrives is never classified, so no other figure can see it.

HorizonDeferrals ulong

How many sequences arrived beyond a reliable Space's ack horizon and so had their retransmit timer withheld rather than started (ADR 0013). It measures a deferral, not a loss: the sequence is not missing and nothing was discarded, only judged too far ahead of [base, base + 32] for this Pump's ack blocks to describe yet, so the timer that would otherwise start ticking toward a spurious retransmission is withheld until the horizon slides over it. This is why it is a Counter and not a Diagnostic (ADR 0013): sustained load with many sequences in flight defers on every Pump, which fails the record test, and it keeps its own identity — rather than folding into OutOfWindowPackets — because counters have a per-Peer scope. Only the two reliable Spaces contribute; the unreliable Spaces have no ack horizon to sit beyond. Rises only under the horizon scenario and stays zero in ordinary operation, where every sequence lands inside the horizon as it arrives. Monotonic and never reset, exactly like OutOfWindowPackets: a Resume carries no counter's history away with it, and this one's lifetime is the Peer's, not the transport's. A freshly connected Peer reads zero. Moves only on the datagram profile. Not derivable: these sequences were admitted, so no refusal figure counts them, and only this one says the ack horizon was outrun.

PacketsRetransmitted ulong

How many packet records this Peer has resent (ADR 0013). Counts packet RECORDS resent, not datagrams sent and not Messages: retransmission is byte-identical at packet- record granularity, because a datagram is repacked on every send and is not itself reproducible — several records can ride one datagram, and the same record can ride a different datagram on retry. This is why it is a Counter and not a Diagnostic (ADR 0013): a retransmit recurs continuously on a lossy path, which fails the record test, and it keeps its own identity — rather than folding into OutOfWindowPackets or HorizonDeferrals — because counters have a per-Peer scope. Monotonic and never reset, exactly like HorizonDeferrals: its lifetime is the Peer's, not the transport's, so a Resume does not zero it. Raised by the retransmit expiry sweep; a freshly connected Peer reads zero. Moves only on the datagram profile. Not derivable: bytes sent mixes first sends with resends, and only this figure separates them.

BytesSent ulong

On the datagram profile, the datagram bytes a flush has handed the transport for this Peer, header included (ADR 0013). Incremented once per Datagram, at the size the coalescing packer actually wrote for it — the 20-byte session header plus every packet record's own header and payload — rather than per record or per payload byte, since header bytes amortising across a Pump's coalesced records is exactly what this figure exists to let a consumer see; counting payload alone would hide that amortisation. Raised regardless of whether the underlying send call reports success, since the bytes were handed to the transport at that point either way — distinct from the Reactor-scope send figure, which counts only a confirmed success. A data Datagram to an Established Peer moves this, and so does each Resume control datagram the dialling end sends it, at its fixed 256 bytes, because a Peer exists to charge. A handshake's control datagrams carry no session id yet to attribute them to, so they are never counted here, on either the sent or the received side (see BytesReceived). On the stream profile, the bytes the socket accepted on this Peer's connection, framing included: every write a Peer is charged a SocketWrites for, handshake and Resume records too, at the count each call reported written. A short write counts the part that went. Monotonic and never reset, exactly like HorizonDeferrals: its lifetime is the Peer's, not the transport's, so a Resume does not zero it. Not derivable: the Reactor-scope datagram figures count datagrams for every Peer at once and lose closed Peers, and the stream profile has no other byte figure.

BytesReceived ulong

On the datagram profile, the datagram bytes attributed to this Peer on arrival (ADR 0013). Incremented once per data Datagram that both names an established Peer's session id and proves well-formed — the same proof that gates ack application and record classification — at the whole Datagram's length, header included, mirroring BytesSent. A Datagram naming no Session, or one so malformed it cannot be attributed to the Peer it claims, charges no Peer: it lands on a Reactor-scope figure instead. A handshake's control datagrams are never counted here either, for the same reason as BytesSent: at the point one arrives, no Peer's session id has been assigned yet for it to name. A Resume that matches this Peer is counted at its fixed 256 bytes, because a Peer exists to charge. A Resume naming no Peer, or presenting the wrong secret, charges none. On the stream profile, every byte read from this Peer's connection, framing and handshake records included. The first record on an accepted connection is charged once it is admitted as this Peer or matched as its Resume. A connection refused or never matched charges no Peer. Monotonic and never reset, exactly like HorizonDeferrals: its lifetime is the Peer's, not the transport's, so a Resume does not zero it. A freshly connected datagram Peer reads zero. Not derivable: MessagesReceived counts Messages rather than bytes, and the Reactor-scope figures neither attribute bytes to a Peer nor see a stream connection.

SocketWrites ulong

How many socket send calls this Reactor has made on this Peer's transport (ADR 0013). One per call, whatever it carried and however it ended — a whole write, a short write and a failed call each count once — because the figure measures what the Reactor paid in syscalls, not what the socket accepted. On the stream profile every write on the Peer's connection counts: handshake and Resume records, delivery-counter records sent alone, and each retention write, where a delivery counter riding that write adds nothing. On the datagram profile it counts one per data Datagram a flush hands the transport and one per Resume control datagram the dialling end sends, beside BytesSent; a handshake's control datagrams are never counted, for the same reason they never reach BytesSent. A rate well above the Pump rate for one Peer names a write path that is not batching. Monotonic and never reset, exactly like HorizonDeferrals: its lifetime is the Peer's, not the transport's, so a Resume does not zero it. Not derivable: how many bytes went out says nothing about how many calls carried them.

ReadShareExhaustions ulong

How many times this Peer had a whole Message ready and was refused Arena room because it had already used its read share for the Frame (ADR 0013, where ReadShareReached became this counter). Counted once per refused reservation. What becomes of the Message differs by profile. The stream profile keeps it buffered and delivers it on a later Pump. On the datagram profile an unreliable record is lost. A reliable one is delivered on a later Pump: a record still held for send order or reassembly is retried from where it is held, and any other is left unacknowledged so the far end retransmits it. Recurs every Pump while one Peer outpaces its share, which is why it is a Counter and not a Diagnostic. Moves on both Session profiles. Monotonic and never reset, exactly like HorizonDeferrals: its lifetime is the Peer's, not the transport's, so a Resume does not zero it. Not derivable: bytes received and MessagesReceived show that delivery lagged arrival, but not that the read share was the cause rather than the Arena itself running out.

Remarks

The shape is shared by both Session profiles; which members move is not. The packet figures (OutOfWindowPackets, DuplicatePackets, UnreliableLossPackets, HorizonDeferrals, PacketsRetransmitted) stay at zero on the stream profile, which has no packets. A member that never moves on a profile is reporting a true zero, not a gap. Every member says, under "Not derivable", what it tells a consumer that the other counters do not (ADR 0013). A field that could not be given that line would not exist.
