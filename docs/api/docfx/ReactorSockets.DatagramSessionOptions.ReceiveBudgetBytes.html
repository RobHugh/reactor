Remarks

Four things per Peer scale with the window, and this figure covers all four. Payload slots — ResolvedFragmentSize bytes each — exist only for the ReactorSockets.DatagramSessionOptions.ReliableSpaceCount Spaces that hold fragments until a Message is whole. The one-byte-per-slot admission record a receive window classifies against exists for all ReactorSockets.DatagramSessionOptions.SpaceCount Spaces, because all four classify whether or not they retain. ReactorSockets.DatagramSessionOptions.FragmentLengthBytes per slot records how many bytes of a held Fragment's payload are actually occupied, and ReactorSockets.DatagramSessionOptions.FragmentGroupEntryBytes per slot names the group that payload belongs to — both exist only for the same ReactorSockets.DatagramSessionOptions.ReliableSpaceCount Spaces as the payload they describe, and both are the receive window's own reassembly bookkeeping, not a separate buffer: the length says a piece was held, the group-identity entry is what still lets an abandoned set's held and declared counts be read once that slot is reused. The six-byte waiting-group entry — ReactorSockets.DatagramSessionOptions.PendingGroupEntryBytes — exists for the same two Spaces too, but only half a window's worth each (ReactorSockets.DatagramSessionOptions.PendingGroupsPerSpace), since a completed-but-undelivered group holds at least two Fragments. This figure is an exact statement of what the receive arena takes at construction. Ordinary records held behind a gap are the one receive-side cost outside it, and they have their own ceiling, HeldRecordBudgetBytes.
