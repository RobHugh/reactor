Send(PeerId, DeliveryMode, ReadOnlySpan<byte>)

Sends message to peer under mode (ADR 0009). A Message too wide for its mode to carry is refused before any work is done on it: no sequence is allocated and no retention is taken, so a rejected Send leaves no trace on the Session. How wide is too wide depends on the mode and is decided by Resolve(int, int, DeliveryMode, uint, int), the one place the rule is stated: an unreliable mode is capped at a single Datagram and refused above it as MessageTooLarge, a reliable mode fragments, and every mode is refused above a second cap as RemoteMessageTooLarge (ADR 0004). That second cap is peer's own announced receive limit, captured on its Slot at handshake, not this Reactor's own MaxMessageSize: Send is therefore not purely local to this Reactor's configuration, because the same payload can be accepted for one Peer and refused for another whose handshake announced a smaller limit. That gate sits behind the peer lookup rather than in front of it, because both caps it measures against, fragment size and remote max message size alike, are the Peer's own captured values; a Peer this Reactor is not holding open returns Closed whatever the Message's width. Past that gate, a reliable mode allocates the next sequence in its own Space and retains the Message whole there, returning RetentionExhausted once that Space has no slot left — and that refusal spends nothing either: the sequence is claimed only once retention has committed, so a refused reliable Send leaves the Space's next sequence exactly where it was, rather than opening a gap the receiver's window would wait on for a record that is never sent; Unreliable and UnreliableSequenced still allocate a sequence — every mode gets one, the same as every other (ReactorSockets.Session.OutboundSequenceSpaces) — but retain nothing, because nothing unreliable is ever retransmitted. A Message this call accepts is queued on peer's Slot (ReactorSockets.DatagramSessionReactor.PeerSlot.PendingSends) and leaves as one packet record in a data Datagram written by a later Pump(), in Send order (ReactorSockets.DatagramSessionReactor.FlushOutboundDatagrams()). Nothing reaches the wire before that Pump runs. One Pump writes a bounded number of Datagrams per Peer (ReactorSockets.DatagramSessionReactor.FlushPeer(ReactorSockets.DatagramSessionReactor.PeerSlot)), so a record queued behind a backlog waits for however many Pumps it takes to reach the front. An unreliable Message is charged its length plus a 7-byte record header against UnreliableQueueBytes and refused with SendQueueFull past it, with nothing copied and no sequence spent.

Parameters

peer PeerId

The Peer to send to.

mode DeliveryMode

Which of the four delivery modes carries this Message; see docs/delivery-modes.md.

message ReadOnlySpan<byte>

The Message payload, unframed. The bytes are copied before this call returns — into ReactorSockets.DatagramSessionReactor._retention for a reliable mode, into the queued record for an unreliable one — so the caller owns its buffer again the instant Send returns and may overwrite or reuse it without changing what is eventually put on the wire. A Message wider than this Peer's send Fragment size (fragmentSize below: the smaller of this Reactor's ResolvedFragmentSize and the peer's announced Fragment size) cannot fit in one Datagram, and for Unreliable and UnreliableSequenced that cap is reported back as MessageTooLarge rather than thrown, and it is permanent — no option lifts it: you may only fragment what you can retransmit (ADR 0004), because fragmenting what cannot be repaired multiplies the failure rate by the number of pieces — a ten-Fragment unreliable Message on a path losing 1% of Datagrams arrives about 90% of the time, having spent ten Datagrams of bandwidth on a coin flip (docs/delivery-modes.md). A Message within that cap but wider than peer's own announced MaxMessageSize is refused with RemoteMessageTooLarge, because the far end would discard it on arrival; a Message over both caps reports MessageTooLarge. For ReliableOrdered and ReliableUnordered the single-Datagram cap does not apply: a Message up to peer's own announced MaxMessageSize (see the summary above) is cut into ceil(length / fragmentSize) Fragments, each retained and sequenced as its own ordinary reliable packet, and a Message wider than that remote limit is refused with RemoteMessageTooLarge. That fragmentSize is this Peer's ReactorSockets.DatagramSessionReactor.PeerSlot.FragmentSize: the smaller of this Reactor's ResolvedFragmentSize and the Fragment size the peer announced, fixed once when the Peer reached Established (ADR 0024) — not re-read on this or any later call, and unchanged by a Resume. A retransmit re-sends bytes already cut, so two Messages sent to the same Peer at different times, and every retransmit of either, are cut with the same size. A reliable Message that needs more Fragments at that size than the peer's announced receive window holds is refused with RemoteMessageTooLarge, with nothing retained or sequenced.

Returns

SendOutcome

Remarks

RetentionExhausted is reachable from one Send call (ADR 0004's "one Message can fill the send window alone"): the retention budget is sized in Fragments, not Messages, so a single Message cut into more Fragments than its Space has free slots for exhausts that Space by itself, with nothing else needing to have sent anything first. The refusal is whole, not partial — this checks the Space's free-slot count against the Fragment count the Message needs before retaining or sequencing a single Fragment, so a refused Send leaves retention holding no Fragment of that Message and leaves the Space's next sequence exactly where Send(PeerId, DeliveryMode, ReadOnlySpan<byte>) found it, the same "spend nothing on a refusal" contract a whole small Message keeps. A half-retained Message would be unrepairable: the receiver's reassembly waits forever for a set that was never cut in full. A smaller Message that fits the Space's free slots still succeeds afterward — the refusal costs the Space nothing.

Sending to a peer this Reactor is not currently holding open — unknown, or already closed — returns Closed rather than throwing, unlike CountersOf(PeerId): a Peer closing under a caller is an ordinary race, the same reason Close(PeerId) tolerates a stale PeerId.

Sending to a peer whose handshake has not reached ReactorSockets.DatagramSessionReactor.PeerPhase.Open returns NotEstablished under every mode, checked before any width gate. Before the handshake the Peer has no remote-announced MaxMessageSize, so a Send would otherwise be misreported as RemoteMessageTooLarge.
